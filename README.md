# 外卖记账（FoodExpenseTracker）

一款个人消费记录 Android 应用，用于记录美团、淘宝闪购、京东三个平台的外卖消费。**首页是日历**：哪天吃了外卖、花了多少一眼可见，点日期就能看到当天吃了什么、评价如何；**订单与评价合并为一条记录**，记一笔时就地写评价。

技术栈：**Kotlin + Jetpack Compose + Room + MVVM（Repository + ViewModel + StateFlow）**。

> **2026-10-24 更新**：新增「**截图识图自动填表**」——选一张外卖订单截图，自动填出店铺/商品/价格/实付，并保留整单商品明细。  
> 实现方式是 **端侧 ML Kit 中文 OCR 认字 + 云端大模型理解版面**，图片不出手机。  
> 这一天的开发过程踩了大量坑（三次换方案、卡了半天的"有概率失败"、两次把真数据压掉的误杀），全部记录在本文件末尾的

## 功能清单

| 模块             | 说明                                                                                                                                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **截图识图（新）**    | 录入页「从订单截图识别」→ 选图 → 自动填出**平台 / 店铺 / 主商品 / 价格 / 数量 / 实付金额**，并额外保留**整单商品明细**。识别结果**只填空字段，绝不覆盖你已输入的内容**；失败时明确提示且不动任何字段                                                                                                                         |
| **实付金额（新）**    | 订单级「实付」字段 = 整单真正付的钱（含打包费/配送费、已扣优惠）。**统计以实付为准**，未填写时回退到「价格 × 数量」                                                                                                                                                                            |
| **商品明细（新）**    | 多商品订单会把**每一件**商品的名字/单价/数量存下来，卡片上列出，供回看"这顿吃了什么"。**明细不参与统计**（单价之和通常不等于实付），可在保存前单条删除                                                                                                                                                          |
| **AI 识别设置（新）** | 日历页 **⋮ → AI 识别设置**：粘贴 API Key、改模型 ID、开关云端、测试连接。Key 用**加密存储**（`EncryptedSharedPreferences`），**不硬编码进 APK**。关掉开关则**全程离线**（走端侧规则）                                                                                                             |
| 日历首页           | 月历采用**暖色底卡片**，与下方记录卡片明显区分；**有外卖的日期整格高亮并加粗显示当天花费**（超 1000 显示为 k），多笔时附"n笔"；今天用白底圈标记、选中日期主色高亮；左右翻月、一键回到今天；顶部显示"本月 N 天有外卖 · ¥X"；**点击日期即列出当天记录**                                                                                                |
| 记录录入           | 订单与评价在同一个表单完成：平台、下单时间、店铺、商品、价格、数量、**实付金额（新）** + 星级（1–5，可选）、评价内容、评价图片；**从日历进入时自动带入所选日期**                                                                                                                                                    |
| 交互方式           | 卡片**只响应长按**（进入编辑页，避免误触），单击不做任何事、也不弹提示；记录页默认展示搜索 + 星级卡片                                                                                                                                                                                     |
| 记录列表           | 记录页**没有标题栏**，顶部留白（按可用高度约 17%，自适应，用于露出背景插画的人物脸部），其下是一行：搜索框 + 平台筛选图标，再下方 **6 张星级卡片**（5★/4★、3★/2★、1★/未评级，两列三行**铺满剩余空间**），每张卡片颜色不同并显示该星级的条数与金额；**点卡片即筛选**，结果按日期分组展示（平台色条 + 星级 + 内容 + 图片缩略图）；**结果页左右滑动（或系统返回手势）即可返回星级卡片**；下滑自动收起搜索框，上滑或回到顶部自动展开 |
| 搜索             | 顶部搜索框，同时匹配**店铺名 / 商品名 / 评价内容**，边输边筛                                                                                                                                                                                                        |
| 筛选             | 星级卡片（5★~1★ / 未评级）+ 平台筛选图标（美团 / 淘宝闪购 / 京东），可与搜索叠加；结果上方显示当前条件并带「清除筛选」                                                                                                                                                                        |
| 统计看板           | 按月或按年查看 **外卖天数**（有订单的日期去重）与 **外卖总金额**（Σ 实付金额，缺失时回退价格×数量），并展示订单数、平台分布、评价情况（已评价数 / 平均星级）                                                                                                                                                     |
| 删除（编辑页内）       | 卡片上没有删除入口：**删除只在编辑页提供**（右上角垃圾桶图标），点击后**二次确认**才真正删除，同时清理评价图片文件                                                                                                                                                                              |
| 图标与背景          | 应用图标为自定义插画（自适应图标 + 各密度圆形/方形图标）；App 内**背景插画不透明铺满**，顶栏完全透明（无白色底衬）；压在图案上的文字统一使用**荧光绿 + 深色描影**（`glowingOnBackground`）保证对比度，卡片内文字仍为深色（卡片是不透明底色）                                                                                                 |
| 一键备份/迁移        | 日历页右上角 **⋮ → 导出全部数据** 生成单个 zip（`data.json` + `images/` 评价图片）；**⋮ → 导入数据** 支持**覆盖导入**（先清空本机再写入，结果与备份完全一致）或**追加导入**（合并）；换手机/分享给别人后导入即可得到一模一样的数据。备份格式当前 **v3**（含实付与商品明细）                                                                      |
| 图片多选           | 系统相册**一次可选多张**（最多 9 张，可多次追加），复制到应用私有目录，无需存储权限                                                                                                                                                                                              |
| 图片压缩           | 相机原图 3~~4MB，**入库时自动压缩**：长边限制 1600px + JPEG 85% + EXIF 方向校正，典型降到 200~~400KB（压缩失败会回退为原样保存不丢图）；旧图可通过 **⋮ → 压缩已有评价图片** 批量压缩，导入备份时也会统一压缩                                                                                                        |
| 图片放大           | **长按（或点击）缩略图**打开全屏查看器：双指缩放、双击放大、拖动平移、多张图片左右切换                                                                                                                                                                                              |
| 输入法适配          | 表单使用 `imePadding()`，键盘弹出时输入框自动避让，写评价不再被输入法遮挡                                                                                                                                                                                               |

### 截图识图是怎么工作的

```
选一张订单截图
   │
   ├─ ① 端侧 ML Kit 中文 OCR（bundled，离线、不依赖 GMS）── 认出文字行 + 坐标
   │
   ├─ ② 云端大模型理解版面（配了 Key 才走）
   │      只发送「文字行 + 坐标」文本，**图片永远不上传**
   │      发送前过滤掉含收货地址 / 手机号 / 订单号的行
   │
   ├─ ③ 云端失败 → 回落到端侧纯规则解析器
   │
   └─ ④ 两级都失败 → 只提示，不动任何已填字段（绝不静默清空用户输入）
```

- **为什么要云端这一层**：端侧规则三年都调不好的那一环不是"字认不出来"，而是**行切错**——价格被切成独立文本行、规格行混进商品、`x1` 不跟商品行合并、划线价与折后价难分。这恰恰是大模型的强项，而 ML Kit 对截图这种印刷体的识字率其实够用。
- **成本**：一张订单截图约几百输入 token + 一两百输出 token，**一次识别约 0.3 分钱**（88 次实测共 ¥0.24）。按每天记 3 笔算，一个月约 ¥0.25（详见[成本实测](#7-成本实测与一次失败的成本优化)）。
- **不出手机的东西**：原图、收货地址、手机号、订单号。

## 数据模型

单表 `meal_records`（订单 + 评价一对一合并）：

| 字段                             | 说明                                                              |
| ------------------------------ | --------------------------------------------------------------- |
| platform                       | 平台（MEITUAN / TAOBAO_FLASH / JD）                                 |
| orderTime                      | 下单时间（epoch 毫秒）                                                  |
| storeName / productName        | 店铺名称 / **主商品**名称                                                |
| productPrice / productQuantity | 主商品价格 / 数量（小计 = 价格 × 数量）                                        |
| **actualPaid**（2026-10-24 新增）  | **订单级实付金额**（含打包费/配送费、已扣优惠）。`null` = 未记录，统计时回退到小计                |
| **items**（2026-10-24 新增）       | **整单商品明细** JSON 数组：`[{name, price, quantity}]`。**不参与任何统计**，仅供回看 |
| starRating                     | 星级 1–5，**null 表示未评价**                                           |
| reviewContent                  | 评价内容                                                            |
| reviewImages                   | 评价图片路径列表（JSON 存储，最多 9 张）                                        |
| reviewTime                     | 评价时间                                                            |
| createdAt                      | 记录创建时间                                                          |

**统计口径唯一入口是 `paidAmount`（= `actualPaid ?: subtotal`）**，日历日汇总、列表分组汇总、统计看板全部走它。  
商品明细**不参与统计**——单价之和通常不等于实付（还有打包费/配送费/优惠），拿它求和会算错钱，有单测钉死这条边界。

数据库版本：**v4**。迁移链完整，无破坏性迁移：

| 迁移      | 内容                                                                                  |
| ------- | ----------------------------------------------------------------------------------- |
| `1 → 2` | 旧的 `orders` + `reviews` 两张表按"订单 + 其最新一条评价"合并进 `meal_records`，历史数据不丢失                |
| `2 → 3` | 新增 `actualPaid`（**可空、不加 DEFAULT**），存量用「价格 × 数量」回填                                   |
| `3 → 4` | 新增 `items`（**非空 + `DEFAULT '[]'`**，实体上标 `@ColumnInfo(defaultValue = "[]")`），老数据为空列表 |

> ⚠️ **两次迁移的写法正好相反**，改迁移前务必看一眼 `Migrations.kt` 里的注释：`actualPaid` 是 Kotlin 可空类型所以必须"可空无 DEFAULT"；`items` 是非空类型所以必须"NOT NULL + DEFAULT"。写反了 Room 的 schema 校验会直接抛 `IllegalStateException`。

## 使用说明

1. **看日历（首页）**：暖色日历卡片上，**有外卖的日子整格高亮并显示当天花费**（多笔会标注"n笔"）；点左右箭头翻月，「今天」一键回到本月；**点击某一天**，下方立即列出当天所有外卖记录。
2. **记一笔**：日历页右下角 `+`（自动带入所选日期）或记录页 `+` → 填平台/时间/店铺/商品/价格/数量/**实付金额** →（可选）点星星评分、写评价、多选图片 → 保存。
3. **用截图识图（新）**：录入页点「**从订单截图识别**」→ 选一张订单详情页截图 → 等几秒，平台/店铺/商品/价格/实付会自动填上。
   - 识别成功会在下方显示「云端识别：…」或「本地识别：…」的核对提示（**来源必须让你看见**，否则识别对了也不知道该继续投哪条路）；多商品时会提示「已保留 N 件商品明细」。
   - 商品明细出现在表单里，**每行右侧 × 可删掉识别错的商品**。
   - **识别结果只填空字段**，你手填过的内容不会被覆盖；识别失败也不会清空任何字段。
4. **配置云端识别（新）**：日历页 **⋮ → AI 识别设置** → 粘贴 API Key → 「测试连接」显示"正常"即可用。
   - **不配 Key 也能用**：只是走端侧规则，准确率低一些，**全程离线**。
   - 首次使用建议先点「测试连接」——连不通时报错就在界面上，不用去翻日志。
5. **编辑 / 补评价**：在日历或记录列表中**长按卡片**进入编辑页（单击不触发任何操作）。
6. **删除**：列表上没有删除入口——进入编辑页后点右上角**垃圾桶图标**，**二次确认**后删除。
7. **按星级筛选（记录页默认）**：搜索框下方 6 张不同颜色的星级卡片铺满整屏，显示该星级条数与金额，**点一下即可查看该星级的全部记录**；在结果页左右滑动、或用系统返回手势即可返回。
8. **搜索**：记录页顶部输入关键字，匹配店铺、商品或评价内容；向下滑动时搜索框自动收起，向上滑动自动展开。
9. **平台筛选**：搜索框右侧的漏斗图标可选美团 / 淘宝闪购 / 京东，与星级、搜索叠加生效。
10. **看图**：**长按（或点击）缩略图** → 全屏查看，双指缩放、双击放大、左右切换。
11. **统计**：切到"统计"标签，按月/按年查看外卖天数与总金额。
12. **导出数据（备份 / 换机 / 分享）**：日历页右上角 **⋮ → 导出全部数据** → 系统文件选择器里选保存位置。备份包含 `data.json`（记录、评价、星级、实付、商品明细）与 `images/`（评价原图）。
13. **导入数据**：**⋮ → 导入数据** → 选 zip → 选择**覆盖导入**（先清空本机再写入，结果与备份完全一致）或**追加导入**（合并）。旧版本备份（无实付/无明细）导入后对应字段为空，记录照常导入。
14. **图片体积**：评价图片保存时自动压缩（最长边 1600px、JPEG 85%）。旧图可点 **⋮ → 压缩已有评价图片** 批量压缩。
15. **外观**：背景插画不透明铺满，顶栏完全透明，压在图上的文字用荧光绿 + 深色描影；想调整可改 `ui/components/AppBackground.kt` 的 `alpha`。

### 性能说明（图片压缩与识图为什么不会卡界面）

- 图片解码 / 缩放 / 重编码全部在 `Dispatchers.IO` 后台线程执行；
- 选图后界面会显示"正在压缩图片（在后台处理，界面不卡）…"，此时按钮置灰；
- **小图跳过重编码**：源图 ≤300KB 直接落盘；
- 识图分两段超时：**端侧 OCR 20s**、**云端 LLM 单独 60s**（共用一个短超时会导致云端永远来不及返回，表现为"静默走本地兜底"）；
- 进入录入页时会**预热 OCR 模型**，点按钮就不用等模型加载。

## 设计要点

- **统计口径**：外卖天数 = 时间段内订单日期（本地时区）去重个数；外卖总金额 = **Σ `paidAmount`（实付，缺失时回退价格×数量）**。统计通过 Room `Flow` 实时响应。
- **实付只能"读"不能"算"**：实付 ≠ 商品原价合计。样例 `43.4 + 1 − 21.9 = 22.5 ≠ 26.4`，所以解析器是"从截图上找到写着的实付"，而不是自己加总推导。
- **商品明细只用于回看**：明细定位是"截图上当时写了什么"，用户手改商品名/价格后明细**不会**自动同步（这是刻意取舍，跟随编辑反而丢原始信息）。
- **搜索实现**：单条 SQL 组合条件（关键字 + 平台 + 星级），关键字用 `LIKE ... ESCAPE '\'` 并转义 `% _`；`flatMapLatest` 保证快速输入时只保留最新查询。
- **数据校验**：店铺/商品非空、价格 > 0、数量 ≥ 1；写了评价内容或加了图片却未选星级时会提示；图片最多 9 张。
- **图片存储**：Photo Picker（无需权限）选中后复制到 `filesDir/review_images`；删除记录或移除图片时同步删除文件。
- **长按交互**：卡片只响应长按（进入编辑），避免误触。
- **错误信息必须可见**：云端失败、识别失败的原因都直接显示在界面上，且**可长按复制**——靠用户截图辨认长报错既累又容易看漏字符。

# 开发日志与经验教训（2026-10-24）

这一节记录「截图识图」功能从零到可用过程中**所有失败尝试与关键判断**。改动 `app/src/main/java/.../ocr/` 下任何代码前，建议先读一遍——下面每一条都是花了真机时间换来的，重复踩一遍代价很高。

## 1. 起点：三个产品决策（先定口径，再写代码）

| 决策点    | 选项                   | 最终选择           | 理由                                                           |
| ------ | -------------------- | -------------- | ------------------------------------------------------------ |
| 记哪个金额  | 商品原价合计 / **实付金额**    | **实付金额**       | 用户真正关心的是"这顿花了多少钱"。实付 ≠ 原价合计（有打包费、配送费、优惠），记原价会算错钱             |
| 多商品怎么记 | 全记 / **只记主商品**       | **只记主商品**（第一版） | 统计口径是整单实付，拆成多条会让"商品单价之和"被当成花费。后来用「方案 A：明细字段」解决了"回看不到其它商品"的问题 |
| 端侧还是云端 | **端侧 OCR + 规则** / 云端 | **端侧**（第一版）    | 用户要求全程本地、离线可用、不依赖 GMS（国产机无 GMS）                              |

**教训**：先定口径再写代码。实付这个口径一旦定错，后面所有规则、所有测试都建立在错误前提上，返工成本极高。

## 2. 第一次真机实测：结果全错

**症状**：店铺名填成 `粉丝群`、商品名填成 `-¥5`、价格与实付都是 `5`。

**根因（结构性，不是词表问题）**：ML Kit 按**视觉分栏**切块，右对齐的价格成了独立 `TextLine`；而解析器假设"一条 TextLine = 一个语义行"。结果两个真实商品全漏，`-¥5` 因为 residue 里剩一个 `-` 号成了唯一"商品"，`itemCount=1` 触发兜底逻辑，价格/实付都被写成 5。

**三个我判断错的细节**（被工程师用真机数据纠正）：

1. **店铺名**的锅不在位置启发式：`STORE_LABEL_RE` 的「商家」匹配到了 `进商家粉丝群` 里的"商家"，标签法先命中并返回"粉丝群" → 必须加 `(?<!进)` 负向断言。
2. **实付错**不是因为"取第一个金额"，而是 `lastPositiveAmountAfter` **在优惠标签处截断**，`合计 已优惠8.5元 ¥12.3` 被整条吃掉 → 改成 `stripDiscountSegments`（整段剥离）。
3. 老 30 条用例的坐标**不是全 0**（`top=100+i*80`），所以几何重建在它们身上真实执行，"全 0 跳过"的保护救不了它们。

**修法**：新增 `rebuildVisualLines()`——按垂直重叠比例聚类（同一视觉带）+ 簇内按 `left` 从左到右拼接，把被切开的名字和价格重新合成一个语义行。

**教训**：解析器里"一条 TextLine = 一行"这种假设，在没有真机数据验证前就是定时炸弹。**在真机上跑一遍，胜过在编造数据上过 100 条测试。**

## 3. 几何层的三次迭代，与三个被否掉的"看起来很对"的方案

三个最终保留的判据（**每个都带反向验证测试：关掉判据，测试必须变红**）：

| 判据                             | 作用                                   |
| ------------------------------ | ------------------------------------ |
| `VERTICAL_ASPECT_RATIO = 3`    | 高 > 3×宽 → 竖排/坏框，强制自成一行（不参与桥接）        |
| `HORIZONTAL_OVERLAP_RATIO=0.5` | 横向大幅重叠 → 判为上下堆叠，**拒绝合并**（这条才是修桥接的正解） |
| `MAX_ITEM_LEFT_LEN = 30`       | 商品名长度上限（原为 14，会误杀 16 字的商品名）          |

**三个"为了压噪声，结果把真数据压掉"的同类 bug**（都是真实数据/用例才暴露的）：

- 14 字长度闸门吃掉 `超大份双人套餐（含可乐薯条鸡翅）`
- `SPEC_FRAGMENT_RE` 无条件删除长度 ≤14 的括号 → 把 `（含可乐薯条鸡翅）` 也删了；改为只删"数字+单位 / 整体命中规格词 / 单字符"三类
- `looksLikeSpec` 用 `contains` 匹配 → `超值套餐(推荐)` 整行被否；改为先剥括号再判断

**被否掉的三个错误方案**（记录下来避免重走）：

- 簇包络比重叠 —— 被高块撑大，`min()` 仍取小块高度，门槛反而更低
- 簇包络高度上限 2.0× 中位行高 —— 误伤"商品名换行成 h=92"的正常块，价格行随之孤立，商品照样消失
- 高块强制成行 —— 同上，更糟

**教训**：压噪声的启发式**一定会误杀真数据**。每加一条"排除规则"，都要问一句"有没有正常数据长这样"，并补一条正向用例。

## 4. PaddleOCR：从选型到下架（完整走了一遍弯路）

**踩的第一个坑：网上教程给的 Maven 坐标全是假的**，实测 404：

- `paddleocr.bj.bcebos.com/maven/` → 404
- `com.baidu.paddle:paddleocr_full:4.0.0` → 404
- `com.tencent.ncnn` → 404；`io.github.rapidocr` → 404

那些"三行代码接入"的文章基本是 AI 生成的，照抄会卡在第一步。

**真实可用的依赖**：`com.microsoft.onnxruntime:onnxruntime-android`（Maven Central 实测存在）。

**关键选型判断**：要用 PP-OCRv4 模型，**走 ONNX Runtime 比 ncnn 划算一个数量级**——一行 `implementation` + 纯 Kotlin 前后处理，无需 NDK/CMake/JNI；ncnn 需要自己编译 so、手写 JNI、实现 DB 后处理与 CTC 解码，3~6 天且极易出细微 bug。

模型获取：**GitHub 直连不通（curl 000），必须走 `hf-mirror.com`**。字典在 SWHL 路径 404，最终从 pypi 的 `rapidocr` yaml 里找到 modelscope 地址才拿到（6623 行）。

**架构上做对的事**：抽 `OcrEngine` 接口让 ML Kit 与 Paddle 并存，POC 调试页可 A/B 切换对比。

**决定性判断（省下了大量时间）**：**换引擎不解决"行切错"**。ML Kit 在失败样本里**字是认对的**（`粉丝群`、`-¥5` 都来自图上真实文字），错的是行框切分与规则。PP-OCRv4 的 DB det 同样会给同一视觉带的左右文本块分别出框。

**下架原因**：真机报 `src.length=480 dst.length=960` 数组越界（手写预处理缓冲的 bug）；加上包体从 32MB 涨到 63.55MB（ORT so 17.5MB + 模型 15.3MB + ML Kit 11MB）。最终整套移除，**归档到 `_archive/paddle-ocr/`（15MB，不参与编译）而不是删除**——之前有过删错文件无法恢复的教训。
（该目录已加入 `.gitignore`，不会进 git 仓库：里面有两个 ONNX 模型二进制，会让仓库永久变大。README 里的记录已足够还原这段经过。）

**教训**：

1. 网上 AI 生成的接入教程，先验证依赖坐标是否存在再动手。
2. **先判断"换方案能不能解决当前的根因"**，再决定换不换。这次根因是行切分，换 OCR 引擎完全对不上症。
3. 归档，不要删除。

## 5. 转向云端：方案 B（ML Kit 认字 + 大模型理解版面）

用户决定放弃纯端侧后，给了两个选项：

| 方案                         | 优点                         | 缺点                              |
| -------------------------- | -------------------------- | ------------------------------- |
| A：只用云端多模态（直接发图）            | 实现简单，能看图                   | **图片要上传**（隐私）、流量大、慢、贵、OCR 精度不可控 |
| **B：ML Kit 认字 + LLM 理解版面** | **图片不出手机**、只发几百 token、便宜、快 | 看不到图，靠坐标推理版面                    |

选 **B**。模型用 `deepseek-flash`（DeepSeek-V4.1-Flash，最便宜档，支持 `effort` 参数）。

**做对的几件事**：

- Key 存 `EncryptedSharedPreferences`，**绝不硬编码进 APK**；模型 ID 做成可配置（平台会改名）
- 发送前用 `PRIVACY_LINE_RE` 过滤地址/手机号/订单号行
- 三级降级链：云端 → 端侧规则 → 手动；任一级失败**不清空**用户已填内容
- `LlmJsonMapper` 写成**纯 Kotlin 解析器**——因为 `org.json` 属于 `android.jar`，在 `isReturnDefaultValues=true` 的 JVM 单测里只返回默认值，测不出任何东西

**教训**：`org.json` 在 JVM 单测里是桩实现。凡是想在单测里覆盖的解析逻辑，都不能依赖它。

## 6. 卡了半天：云端"有概率失败"，真因是 `max_tokens = 800`

**症状**：同一张截图，第一次失败、第二三次成功、第四次又失败。报错是 `云端识别未生效…未返回可解析的 JSON：`——**冒号后面一片空白**。

排查过程中一共修掉 4 个只在真机暴露的 bug：

1. **`testConnection()` 复用了"必须是 JSON"的解析函数**，而测试请求要的是纯文本 → 必现失败。
2. **外层 20s 超时包住了 LLM 调用**，而 LLM 的读取超时是 45s → 外层先掐断，**静默走本地兜底**，从界面上看不出来。
3. LLM 偶尔在 JSON 前后带一句解释文字 → 解析器改成取「第一个 `{` 到最后一个 `}`」之间的内容。
4. **根本原因：`max_tokens = 800` 太小**。V4 系模型默认 `effort=high` 带推理，**推理过程吃光了 800 token**，正文还没开始写就被截断 → HTTP 200 但 `content` 是**空字符串**（`finish_reason=length`）。改成 3000 后，用户实测 **3 张不同订单截图 × 每张 4~5 次 = 100% 成功**。

**教训（这一天最有价值的一条）**：

- **报错信息里"没有什么"和"有什么"同样重要**。空正文这个线索是靠用户逐字复述红字才发现的——如果报错只截前 200 字，人的注意力会被引向完全错误的方向。
- 所以现在报错里**强制带上 `finish_reason` + 正文长度 + 原文**，且界面上**可长按复制**。
- **超时必须分级**：不同阶段的合理耗时差一个量级，共用一个超时会制造"静默降级"这种最难排查的故障。
- **静默降级是敌人**。任何降级路径都要在界面上留下可见痕迹（现在会显示"云端识别未生效，已回退本机规则：原因"）。

## 7. 成本实测与一次失败的成本优化

- 实测 **88 次调用共花 ¥0.24**（第一次复盘时误读成 ¥2.4，差了一个数量级，已更正）。折算**单次不到 ¥0.003**，也就是**每笔不到 0.3 分钱**。  
  按每天记 3 笔估算，**一个月约 ¥0.25**——基本可以忽略。
- **真正的成本大头是输入 prompt 和模型推理**，跟商品数量无关。后来加"商品明细"只在输出端多几十 token（占比 **1~3%**），基本不影响花费。
- **一次失败的成本优化（已回退，别再试）**：试过在 prompt 开头加「不要任何推理、分析、思考过程，第一个字符必须是 `{`」，想压低推理 token。实测**反而暴涨**：汉堡 1234 → 1655，煎饼王 596 → 2411（**+304%**）。模型会花更多 token 去思考"怎么才能不思考"。这条已写进 `LlmOrderParser.SYSTEM_PROMPT` 的注释里。
- 为了能看见成本，界面上会显示每次调用的 `用量：N+M tokens（推理 X），json=on,effort=low`——**实际生效的参数档位也一起显示**（参数降级逻辑会在收到 400 时自动去掉 `response_format`/`effort`，不记录的话"我以为关了其实没关"从外表永远看不出来）。

**教训**：

- 优化 LLM 成本前先**量化**。凭直觉加的"少思考"指令，实测能让成本翻三倍。
- **看账单要看清小数点**。本次复盘时把 ¥0.24 误读成 ¥2.4，差点得出"月成本两三元、需要认真优化"的错误结论——而真实成本根本不值得为它牺牲准确率。
- 结论：**单次不到 0.3 分钱的情况下，除非调用量上两个数量级，否则不要为了省 token 去动 prompt**。准确率远比这点费用值钱。

## 8. 方案 A：商品明细字段（DB v3 → v4）

多商品订单只留主商品，用户回看不到"这顿还吃了什么"。解法是**加一个明细字段，而不是把一条记录拆成多条**——拆多条会让统计把"商品单价之和"当成花费，而它不等于实付。

**两次迁移写法完全相反**（这是本次最容易踩的坑）：

| 字段           | Kotlin 声明                 | 迁移 SQL 必须写成                                     | 还要做什么                                |
| ------------ | ------------------------- | ----------------------------------------------- | ------------------------------------ |
| `actualPaid` | `Double?`（可空）             | `ADD COLUMN actualPaid REAL`（**可空、不加 DEFAULT**） | 无                                    |
| `items`      | `List<OrderItem>`（**非空**） | `ADD COLUMN items TEXT NOT NULL DEFAULT '[]'`   | 实体加 `@ColumnInfo(defaultValue="[]")` |

**已反向验证**：故意把 `MIGRATION_3_4` 写成 `ADD COLUMN items TEXT`（照搬上一次的可空写法）后，`Migration3To4Test` 的 3 个用例**全部变红**（`IllegalStateException at RoomOpenHelper.kt:93`），恢复后全绿。证明这些用例有判别力，不是"怎么写都过"。

**其它要点**：

- 明细**不参与统计**，有单测钉死：实付 12.3、明细求和 20.7 → 断言 `paidAmount == 12.3`
- 明细是**附属信息**：坏 JSON 一律降级为空列表，绝不让整条主记录读不出来
- 主字段全空、只有明细时**仍判识别失败**（明细不能单独撑起一条记录）
- 卡片上 `items.size > 1` 才展示（1 件时与商品行重复），且**刻意不显示合计**——显示合计会被误当成花费

## 9. 流程与协作教训

- **多会话/多人写同一仓库前，必须先确认没有别人在写**。本次事故：工程师把另一个会话产出的 `util/ocr/OcrEngine.kt`、`OrderTextParser.kt` 当重复实现删掉了，项目没有 git，最终未能恢复。**删除任何非自己产出的文件前必须先问。**
- **临时探针文件必须在创建它的同一条命令里删掉**。本次 QA 三次把 `fail()` 探针（BridgeProbe / ThirdRoundProbe）留在制品里，导致构建变红、取不到"字面绿"。
- **反向验证是刚需**：每个修复都要问"关掉它，测试会不会变红"。不红的测试等于没有测试。
- **断言"某修复没有测试守护"之前必须先 grep**。本次 QA 误判过一次——实际有 `geometry_两行高宽块不做桥接` 且已反向验证过；另一次把失败原因归错了（`MAX_ITEM_LEFT_LEN=14` 杀掉了 16 字商品名，不是桥接问题）。
- **报错必须可见、可复制**。靠用户截图辨认长报错，既累又容易看漏字符。

## 10. 环境坑（本机）

- 项目根目录**没有 `gradlew` / `gradlew.bat`**（只有 `gradle/wrapper/gradle-wrapper.properties`），PATH 里也没有 gradle。命令行构建要么先 `gradle wrapper` 生成，要么直接用缓存的分发包。
- `JAVA_HOME` 环境变量指向的路径**可能根本不存在**（本机指向的 `.../jbr` 不存在，真 JDK 在 `.../AS0827/jbr`）。用 `java -version` 确认后再传给 Gradle。
- 用户 IDE 同时构建会踩坏 `app/build`（dex 冲突、多个 Kotlin daemon）。命令行构建前最好先停掉 IDE 的构建。

### 仓库里**不包含**什么

| 文件或目录                              | 为什么不在仓库里                                     |
| ---------------------------------- | -------------------------------------------- |
| `_archive/`                        | 下架的 PaddleOCR 方案归档，含两个 ONNX 模型二进制（15MB），会让仓库永久变大。本地仍在 |
| `keystore.properties` / `*.keystore` | 签名文件与口令，**绝不能进仓库**                           |
| `local.properties`                 | 本机 Android SDK 路径（含用户名）                      |
| `app/build`、`app/release`           | 构建产物                                         |

> **首次打正式包前需要自己生成签名配置**：`release.keystore` 不在仓库里。
> 执行 `powershell -ExecutionPolicy Bypass -File tools\make-keystore.ps1` 即可自动生成；
> 不配也能构建，只是 release 会退回 debug 签名（详见[第 5 节](#5-安装到华为--鸿蒙harmonyos设备)）。

### 想复现识图功能？

识图依赖云端大模型时需要自备 API Key，在 App 内「AI 识别设置」里填写，**Key 不会进仓库**（`AiSettings` 只在运行时读加密存储，代码里没有任何默认值）。

不填 Key 也能用，会走端侧规则兜底，全程离线。
